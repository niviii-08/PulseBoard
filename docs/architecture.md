# PulseBoard architecture

This replaces the previous `docs/api.md`, `architecture.md`, `database.md`,
`deployment.md`, and `security.md`, which described PulseBoard's earlier
life as an uptime-monitoring tool and are no longer accurate after the
pivot to a social intelligence platform. Rewriting all five to the same
depth wasn't done in this pass — this single doc covers what actually
exists today; deployment/security reference docs are a documented gap
(see README's "Remaining limitations").

## Data pipeline

```
COLLECTORS (Reddit / News / YouTube / X / Demo)
        |
        v
INGESTION (app/services/pipeline.py::ingest_normalized_posts)
   - sentiment scoring (VADER)         -> app/services/sentiment_engine.py
   - topic assignment (keyword overlap) -> app/services/topic_service.py
        |
        v
        Mention rows in Postgres
        |
        v
ENGINE PIPELINE (pipeline.py::run_pipeline_for_topic / _for_brand)
   - trend scoring        -> app/services/trend_engine.py
   - propagation analysis -> app/services/propagation_engine.py
   - brand risk scoring   -> app/services/risk_engine.py
   - AI explanation       -> app/services/explanation_engine.py
   - alert generation     -> app/services/alert_engine.py
        |
        v
        TrendSnapshot / PropagationEvent / RiskAssessment / AIInsight / Alert
        |
        v
API (app/api/v1/endpoints/*.py) -- read-only, serves the last computed
   snapshot; never recomputes an engine on a GET request
        |
        v
FRONTEND (React/Vite/TS) + WebSocket relay for realtime alert/risk events
```

Every engine in `app/services/*_engine.py` is a pure function (no DB
access, no I/O) and is unit-tested directly in `app/tests/test_*_engine.py`.
`app/services/pipeline.py` is the only module that both calls the engines
and talks to the database — it's intentionally thin, mostly plumbing.

## Data model

- `Topic` — a detected subject of conversation, clustered by keyword
  overlap (`app/services/topic_service.py`).
- `Mention` — one normalized post from any platform (mirrors
  `app.collectors.base.NormalizedPost`).
- `TrendSnapshot` — one engine run's momentum score for a topic, at a
  point in time (bucketed hourly by `pipeline.rebuild_trend_snapshots`).
- `PropagationEvent` — which platform first carried a topic and in what
  order, derived from real `Mention.posted_at` timestamps.
- `Brand` — a monitored brand, matched against posts by keyword/alias.
- `RiskAssessment` — one risk-engine run for a brand, with an explicit,
  capped point breakdown (`drivers`) rather than an opaque score.
- `AIInsight` — a generated "why trending" / sentiment-shift explanation,
  stored with the structured `evidence` it was grounded in.
- `Alert` — a threshold-crossing notification, generated by
  `app/services/alert_engine.py`.

Full column-level detail is in the ORM models themselves
(`backend/app/models/trend.py`, `backend/app/models/social.py`) and the
Alembic migrations (`backend/alembic/versions/`) — both are kept
docstring-heavy specifically so they don't need a separate schema doc
to stay in sync with.

## API surface

See `backend/app/api/v1/router.py` for the full route table, or run the
backend and open `/docs` (FastAPI's auto-generated OpenAPI UI) for live,
always-accurate endpoint documentation — deliberately not duplicated
into a static markdown file that can drift from the code.

## Demo data

`app/collectors/demo.py` scripts a small number of causal scenarios
(a product-launch battery complaint that propagates Reddit -> X -> News
-> YouTube, and a Nike delivery-delay brand crisis) rather than emitting
independent random numbers, so the propagation/risk/trend engines have
something real to demonstrate. Every demo-sourced `Mention` is flagged
`source_is_demo=True`, and the frontend renders a "Demo data" badge
wherever those posts are shown.

## What's real vs. what's a documented gap

- **Real, working, tested:** every engine, the demo data pipeline, the
  full API, the news/RSS collector (implemented correctly, but not
  exercisable in the sandboxed environment this was built in — see its
  docstring), the frontend against both mock data and the live API
  contract.
- **Honest stubs, not fake:** Reddit and YouTube collectors report
  `not_configured` and return no data until real API credentials are
  supplied; X is marked `optional` by design (see `app/collectors/x.py`).
- **Documented gap, not attempted:** BERTopic/embedding-based topic
  clustering (keyword-overlap clustering was used instead — see
  `app/services/keyword_extraction.py`'s docstring for the tradeoff);
  outbound alert emails/webhooks (the email-sending scaffolding from the
  previous product still exists in `app/services/email_sender.py` but
  isn't wired to the new Alert model); per-topic API/database/deployment/
  security reference docs.
